# Changelog

## 0.5.4 — 2026-09-17 — Enter снова переносит строку

Проблема: на сайте, где Enter переносит строку, а отправка — Ctrl+Enter, защита перехватывала обычный Enter и не давала сделать отступ.

Причина: в правиле сайта осталось значение по умолчанию «Отправка с клавиатуры: Enter» — защита блокировала каждый Enter в поле с непереведённым текстом.

Исправлено:
- Новый режим **«Авто»** (по умолчанию): проверяются Ctrl/⌘+Enter и кнопка отправки. Обычный Enter **не блокируется никогда**; расширение само замечает, отправляет ли сайт по Enter (после Enter поле опустело) — только тогда Enter тоже начинает проверяться. Если Enter переносит строку, режим не меняется.
- Все правила со значением «Enter» один раз автоматически переводятся на «Авто». Явно выбрать «Enter», «Ctrl+Enter», «Shift+Enter» или «Только кнопкой» по-прежнему можно — выбор после обновления сохраняется.
- Диагностика: `guard.sendKey` и `guard.enterLearned` (заметило ли расширение отправку по Enter).
- Тестовый чат: `?ctrlsend=1` — Enter переносит строку, отправка по Ctrl+Enter.

Проверено: в режиме «Enter переносит строку» Enter с русским текстом в испанском тикете не блокируется и не отменяется, отправка по Enter не «заучивается»; Ctrl+Enter — предупреждение. В режиме «сайт отправляет по Enter» первый Enter проходит, расширение запоминает это и дальше проверяет Enter. Миграция: «enter» → «auto» один раз, повторно выбранный «enter» сохраняется.


## 0.5.3 — 2026-09-17 — защита срабатывает всегда, картинки в ответе сохраняются

### Защита от отправки без перевода «не работала»
Причины:
- Если язык собеседника не определён (пишет по-английски — английский не переводится, или сообщения ещё не переведены), защита молча пропускала отправку. Поэтому русский текст спокойно уходил в английские тикеты.
- Проверялось только сочетание из правила сайта: при отправке по Ctrl+Enter и правиле «Enter» (или «Shift+Enter») клавиатурная отправка не проверялась.

Исправлено:
- **Язык собеседника не определён** → защита блокирует отправку, определяет язык по сообщениям тикета; если определить нельзя — ожидает ответ на языке по умолчанию для ответов (английский). В предупреждении: «Язык собеседника не определён — ответ ожидается на: Английский».
- **Ctrl/⌘+Enter проверяется всегда** (им почти везде отправляют); сочетание из правила — как раньше. Обычный Enter и Shift+Enter (перенос строки) не трогаются, если они не выбраны в правиле. Программное «нажатие на кнопку» после проверки делается только для сочетания из правила.
- Пока оператор печатает, язык собеседника определяется заранее — при отправке ждать не нужно.
- **Диагностика**: в отчёте поле `guard` — последнее решение защиты и причина («язык совпал: en», «письменность Cyrillic ≠ es», «не найдено поле ввода», «режим заметки: …»), `sendKey`, `sendGuard`. Текст сообщения в отчёт не попадает.

### Картинки в ответе пропадали
- Причина: при вставке перевода поле очищалось целиком и заполнялось текстом.
- Теперь, если в поле есть картинки (а также видео, фреймы, вложения), текст заменяется **по абзацам**: каждый абзац и пункт списка получает свою строку перевода, блоки с картинками не читаются, не переводятся и остаются на своих местах. Если строк в переводе больше — лишние добавляются абзацами в последний текстовый блок; если меньше — оставшиеся абзацы очищаются, картинки всё равно остаются.
- Если разобрать структуру поля не удалось, поле не изменяется: перевод копируется в буфер обмена с подсказкой вставить вручную.
- То же для «↩ Вернуть оригинал».

Проверено на тестовом чате: английский тикет — Ctrl+Enter с русским текстом → предупреждение, с английским → отправка; испанский тикет — Ctrl+Enter с русским текстом → предупреждение; поле с 2 картинками, пустой строкой и списком — после вставки перевода картинки на месте, текст переведён по абзацам, вставка распознана как перевод.


## 0.5.2 — 2026-09-17 — Shift+Enter для отправки, без Ctrl+Shift+Y, совместимость с macOS

### Отправка по Shift+Enter
- Новый вариант «Отправка с клавиатуры» в правиле сайта: **Shift+Enter (Enter — новая строка)**. Защита проверяет только Shift+Enter; обычный Enter (перенос строки) больше не перехватывается.
- Раньше защита игнорировала любые нажатия с Shift и проверяла обычный Enter — на сайтах, где Enter переносит строку, это мешало писать многострочные ответы.
- Повторная отправка после проверки воспроизводит то же сочетание (Shift+Enter, Ctrl/⌘+Enter).

### Убрано сочетание Ctrl+Shift+Y
- На сайте поддержки оно уже занято (закрывает чат). Команда переименована (`translate-reply`) и **не имеет сочетания по умолчанию** — у тех, кто обновляется, старое назначение пропадает. Своё сочетание можно задать в `chrome://extensions/shortcuts`; popup показывает назначенное.
- Перевод ответа — кнопкой «🌐 Перевести» у поля ввода. Упоминания Ctrl+Shift+Y убраны из интерфейса и документации.

### macOS
Проверено: манифест, горячие клавиши, модификаторы, шрифты, ввод через IME.
- Подсказки на Mac показывают ⌘ вместо Ctrl (`⌘Enter — вставить` в панели перевода).
- Вставка перевода в панели — Ctrl+Enter или ⌘+Enter; сохранение настроек — Ctrl+S или ⌘+S (уже работало).
- Режим «Ctrl+Enter» сайта: на Mac проверяется и ⌘+Enter, повторная отправка отправляет ⌘+Enter.
- Ввод с IME (японский, корейский, китайский): Enter, подтверждающий выбор иероглифов, не считается отправкой (в т.ч. `keyCode 229`).
- Моноширинный шрифт в проверках и глоссарии: добавлен Menlo. Остальной интерфейс — системный шрифт (San Francisco на Mac).
- Встроенный переводчик Chrome (Translator / Language Detector API) доступен на macOS в Chrome 138+ так же, как на Windows.
- Тестовый стенд: `?mac=1` эмулирует macOS.
- Скрипты `tools/*.ps1` — только для разработки (Windows / PowerShell); для работы расширения не нужны.

Проверено на тестовом чате с эмуляцией macOS: подсказка `⌘Enter`; при режиме Shift+Enter обычный Enter не вызывает предупреждение, Shift+Enter с русским текстом в испанском тикете — предупреждение.


## 0.5.1 — 2026-09-17 — кнопка отправки работает, письма пользователей снова переводятся

### Кнопка отправки «не отправляла»
Причины:
- «Кнопка отправки» в правиле указывала на обёртку с несколькими кнопками (отправка, эмодзи, вложения). Защита отправки перехватывала клик, проверяла язык и повторяла отправку программным кликом по обёртке — сайт такой клик игнорирует.
- Многие сайты вообще не принимают программные клики и Enter.
- После вставки многострочного перевода редактор перестраивает абзацы, и защита не узнавала вставленный перевод — поэтому проверка запускалась даже для него.

Исправлено:
- **Проверка языка заранее**: пока оператор печатает (пауза 0,5 с), язык текста проверяется без облака (CLD и встроенный детектор). Если язык совпадает с языком ответа — клик/Enter не перехватывается, сайт получает настоящее нажатие.
- **Если сайт не принял повторную отправку**: через 1,2 с, если текст всё ещё в поле, появляется подсказка «✔ Язык проверен — нажмите «Отправить» ещё раз»; следующая отправка этого текста проходит без проверки (60 с).
- Повторная отправка кликает по **реально нажатой кнопке** (с pointer/mouse-событиями), а не по обёртке.
- Если селектор кнопки — обёртка с несколькими кнопками, перехватывается только кнопка отправки (send/submit/reply/отправ в `data-testid`, `aria-label` или тексте); клики по эмодзи, вложениям и т.п. не трогаются.
- Вставленный перевод узнаётся без учёта переносов строк и пробелов.
- Пикер «Кнопка отправки»: при клике мимо кнопки берёт единственную кнопку внутри; предпочитает короткий селектор по `data-testid` (например `button[data-testid="send-button"]`); id, сгенерированные фреймворком (`base-ui-_r_fb_`, `:r1:`, `radix-…`), больше не попадают в селекторы.

### Письмо пользователя не переводилось
- Причина (отчёт диагностики): при поиске тела письма внутри «Сообщения пользователя» первым попался служебный блок — предупреждение о внешнем отправителе с кнопкой «Add as participant» (класс `text-caption` принимался за признак текста). Переводилась кнопка, а само письмо — нет.
- Теперь кнопки, предупреждения, уведомления и баннеры не считаются телом сообщения; утилитарные классы (`text-*`, `bg-*`, `border-*`…) не считаются признаком текста; выбирается блок с основным текстом (≥60% самого длинного), из вложенных — самый внутренний.

Проверено на тестовой странице с такой же разметкой: письмо переведено с сохранением абзацев, предупреждение не тронуто; клик по «эмодзи» внутри обёртки не перехвачен; испанский ответ после набора отправлен с первого клика; при сайте, игнорирующем программные клики, — подсказка и отправка вторым кликом.


## 0.5.0 — 2026-09-17 — ответы только на языки платформы

Задача: платформа поддерживает английский, французский, португальский, итальянский, испанский, немецкий, корейский, японский и арабский. Отвечать нужно только на этих языках; сообщения пользователей по-прежнему переводятся с любого языка.

Добавлено:
- **Настройка «Языки ответов»** (`replyLangs`, раздел «Исходящие сообщения»): галочки для всех языков расширения. По умолчанию включены `en, fr, pt, it, es, de, ko, ja, ar` (выделены жирным), остальные выключены. Кнопки «Только языки платформы» и «Включить все». Хотя бы один язык всегда остаётся включённым.
- **«Если язык собеседника выключен — отвечать на»** (`replyFallbackLang`, по умолчанию английский): список из включённых языков.
- В панели перевода ответа список «→ язык» содержит только включённые языки.
- Если собеседник пишет на выключенном языке (например, турецкий), ответ переводится на язык по умолчанию для ответов, в панели — пометка «язык выключен для ответов, перевод на „Английский“» с подсказкой, где включить. Кнопка у поля ввода показывает язык, на который реально уйдёт ответ.
- **Защита отправки** ждёт ответ на языке, на который его можно переводить: при выключенном языке собеседника — на языке по умолчанию для ответов; в предупреждении указаны оба языка.
- Входящие сообщения, тема, письма и сообщения агентов переводятся как раньше — со всех языков.
- Старые настройки обновляются автоматически: если списка языков ответов нет, включаются языки платформы.

Проверено на тестовом чате: турецкий тикет — входящие переведены, в панели ответа 9 языков, выбран английский, показана пометка; после включения турецкого в настройках — турецкий в списке и выбран автоматически; защита отправки для русского текста в турецком тикете предлагает перевод на английский; страница настроек сохраняет `replyLangs` и `replyFallbackLang`.


## 0.4.4 — 2026-09-17 — перевод сохраняет абзацы, пустые строки и списки

Проблема: перевод ответа приходил одним сплошным абзацем — пропадали переносы строк, пустые строки между абзацами и пункты списка.

Причины:
- Встроенный переводчик Chrome (используется первым с 0.4.1) переводит текст одним куском и склеивает строки.
- Пункты списка в редакторе ответа читались без маркеров.

Исправлено:
- **Построчный перевод на устройстве**: текст разбивается на строки; пустые строки (в т.ч. из неразрывных пробелов), отступы и маркеры списков (`*`, `-`, `•`, `1.`, `1)`) сохраняются как есть, переводится только текст каждой строки; результат собирается в исходной структуре. Строки без букв (эмодзи, суммы) не переводятся. Глоссарий проверяется по каждой строке.
- Мост встроенного переводчика переводит все строки одним вызовом (`localTranslateMany`), без отдельного сообщения на строку.
- **Списки в поле ответа** читаются с маркерами: `• пункт` (нумерованные — `1. пункт`), поэтому переживают перевод и вставку.
- Это же исправляет склеенные абзацы в переводах входящих писем.
- Проверено на тексте ответа из тикета (абзацы, пустые строки, список из 2 пунктов) с эмуляцией склеивания строк встроенным переводчиком: 14 строк на входе — 14 на выходе, каждая строка переведена отдельно, маркеры и пустые строки на месте, вставлено 14 абзацев.

## 0.4.3 — 2026-09-17 — сообщения пользователя находятся сами, тема в шапке видна

### Письмо пользователя не переводилось
- Причина (отчёт диагностики): «Сообщение» указывало только на один вид сообщений (`content-part-content` — ответы/бот), а письмо пользователя размечено иначе (`user-email-content`). Найдено было только английское письмо бота (`agent: 1, user: 0`).
- Теперь внутри каждого «Сообщения пользователя», где «Сообщение» ничего не нашло, расширение **само находит тело сообщения**: потомок с `data-testid`/классом со словами content / body / message / text / email-html (служебные — actions, pill, header, meta, avatar, timestamp, footer, toolbar — исключаются), самый внутренний, содержащий основной текст. Шапка письма (имя, адрес, «to:») и кнопки в перевод не попадают.
- Проверено на разметке из отчёта: письмо пользователя (португальский) найдено и переведено, письмо бота осталось сообщением агента.

### Тема в шапке переведена, но не видна
- Причина: сайт перерисовывает шапку и снимает класс, которым прятался оригинал; перевод оказывался после оригинала в обрезанной строке (за «…»).
- Теперь перевод темы ставится **в начало строки** (`🌐 перевод · оригинал`), оригинал не прячется — перевод виден всегда, даже в обрезанной шапке. Полный перевод и оригинал — во всплывающей подсказке.
- **Если сайт удалил перевод** (перерисовал элемент с тем же текстом) — расширение замечает удаление и показывает перевод заново. Это же работает и для подписей переводов сообщений и кнопок «🌐 перевести».

## 0.4.2 — 2026-09-17 — язык ответа из текущего тикета, панель не выходит за экран

### Язык ответа брался из предыдущего тикета
- Причина: если в тикете не находились переведённые сообщения пользователя (например, «Сообщение» настроено только на входящие письма), панель подставляла «последний язык на сайте» (`lastOutgoingLang`) или язык, найденный на вкладке раньше, — то есть язык прошлого тикета (немецкий чат → испанский).
- Теперь язык ответа определяется **только по текущему тикету**:
  1. 📌 закреплённый; 2. переведённые сообщения пользователя; 3. письмо во фрейме;
  4. **определение по тексту сообщений пользователя на странице** (по «Сообщение пользователя», без облака — встроенным детектором Chrome), даже если «Сообщение» настроено неточно;
  5. язык, который оператор уже выбирал **в этом тикете**;
  6. «Язык по умолчанию» из настроек.
- «Последний язык на сайте» больше не используется; вместо него — память языка по тикету (`ticketLangs`, 500 последних тикетов).
- Язык, найденный на вкладке, привязан к тикету и не переносится в другой.
- При открытии тикета язык определяется заранее (через 2,5 с) — защита отправки и кнопка «Перевести → DE» сразу знают язык нового тикета.
- Проверено на тестовом чате с неработающим «Сообщение»: испанский тикет → `es`, немецкий → `de`, турецкий → `tr`, снова испанский → `es`.

### Панель перевода выходила за экран на длинных сообщениях
- Высота панели ограничивается свободным местом над полем ввода (или под ним, или весь экран по центру, если места мало); шапка с выбором языка и кнопка «Вставить перевод» всегда видны.
- Длинный текст прокручивается внутри: поля оригинала/перевода — до 38% высоты экрана, обратный перевод — до 30%, общий блок — прокрутка.
- Панель пересчитывает положение при изменении размера окна.
- Проверено: 14 абзацев текста — панель целиком в экране, шапка и кнопка видны.

## 0.4.1 — 2026-09-17 — сначала скачанный переводчик, потом облако — для всего

Проблема (тест на реальном хелпдеске): при блокировке бесплатного Google перевод не работал вообще, хотя языковые пакеты скачаны. Причины:
1. Перевод ответа в панели всегда шёл в облако (встроенный переводчик был только для входящих и обратного перевода).
2. Встроенному переводчику нужен известный язык оригинала, а в панели его определял Google.
3. Скрипт на странице сайта работает в отдельном окружении, где Translator API может отсутствовать, — хотя на странице настроек (страница расширения), где скачивались пакеты, он есть.
4. Пакеты скачивались только в одну сторону (язык → английский), а для ответа нужны пары «язык оператора → язык пользователя».

Исправлено:
- **Новый режим по умолчанию «Для всего»** (`localTranslatorMode: 'all'`): скачанный переводчик Chrome используется первым для входящих, перевода ответа, обратного перевода и определения языка; облако — только если перевести на устройстве нельзя. ## 0.4.0 — 2026-09-17 — меньше запросов к Google, перевод на устройстве, резерв Google Cloud

Причина: бесплатный Google несколько раз за день ограничивал IP (перенаправление на страницу проверки) даже при ~170 запросах.

### 1. Меньше запросов
- **Перевод только видимых сообщений** (`onlyVisible`, по умолчанию вкл). Сообщение переводится, когда оно на экране или рядом (±600px) — через IntersectionObserver (работает и в Shadow DOM). История тикета выше экрана не переводится, пока до неё не долистали. Проверено: из 43 сообщений переведены только видимые 3, после прокрутки вниз — ещё 4 появившихся.
- **Объединение запросов** (`batchRequests`, по умолчанию вкл). Сообщения одного языка (по встроенному детектору Chrome), пришедшие в течение 150 мс, уходят одним запросом (до 20 сообщений / 3500 символов):
  - бесплатный Google — тексты склеиваются через метки `⟦900001⟧`; если после перевода частей не столько же — сообщения автоматически переводятся по одному;
  - Google Cloud — нативный массив `q`, язык определяется для каждого текста.
  - Проверено на подменённом ответе: 3 сообщения → 1 запрос; при «съеденных» разделителях — корректный перевод по одному.
- **Постоянный кэш переводов** в `storage.local` (раньше — до перезапуска браузера): до 3000 записей, срок 30 дней, старые удаляются автоматически. Повторно открытые тикеты не переводятся заново. «Очистить кэш» чистит и его.
- Статистика: «переведено на устройстве», «сообщений объединено».

### 2. Перевод на устройстве (встроенный переводчик Chrome)
- Новый модуль `content/local-translator.js` — Translator API и Language Detector API (Chrome 138+): перевод прямо в браузере, **без сети, без лимитов, тексты не уходят в Google**.
- Настройка **«Перевод на устройстве»** (`localTranslator`): для входящих и обратного перевода (по умолчанию) / только входящие / не использовать. Перевод ответа пользователю всегда идёт в облаке (качество важнее).
- Язык источника: встроенный детектор Chrome (CLD), если уверен; иначе Language Detector API (уверенность ≥ 0,7). Без уверенного языка — облако.
- Используются только **уже скачанные** языковые пакеты (скачивание требует клика). Настройки → «Перевод на устройстве» → **«Проверить пакеты»** / **«Скачать языковые пакеты»** для списка языков собеседников.
- Глоссарий работает: если метки терминов не пережили перевод на устройстве — сообщение переводится в облаке.
- **Защита от зависания API**: таймауты (проверка пакета 3 с, создание 10 с, перевод 15 с) → облако; после 3 зависаний встроенный переводчик отключается до перезагрузки страницы. Проверено: при не отвечающем API сообщение переведено облаком за 3,3 с.
- Подпись перевода показывает источник: «на устройстве (Chrome)», «Google», «Google Cloud».
- Диагностика: `found.localTranslator` (наличие API, недостающие пакеты), `onlyVisible`.

### 3. Резерв Google Cloud
- При ограничении/недоступности бесплатного Google (в т.ч. во время паузы предохранителя) запросы **сразу идут в Google Cloud** — и одиночные, и объединённые. Проверено на подменённых ответах: бесплатный 429 → оба сообщения в Cloud одним запросом; следующий запрос во время паузы — сразу в Cloud, бесплатный не запрашивается.

- Диагностика: `cloudFallback` (резерв настроен), `translator.cooldown` (какой провайдер на паузе и сколько секунд).

## 0.3.1 — 2026-09-17 — по итогам теста на реальном хелпдеске

### Сообщения агентов — перевод по кнопке
- Новое поле правила **«Сообщения агентов»** (`agentMessages`): **по кнопке** (по умолчанию) / автоматически / не переводить.
- Агент = сообщение, которое не попадает под «Сообщение пользователя» (`userMessageSelector`). Без этого селектора все сообщения считаются сообщениями пользователя (как раньше).
- В режиме «по кнопке» у сообщения агента — маленькая кнопка **«🌐 перевести»**; запрос к переводчику уходит только после клика. Английские сообщения (по встроенному детектору Chrome) кнопку не получают.
- Запрошенный перевод держится при обновлениях ленты (запоминается по хэшу текста); если текст сообщения изменился — снова кнопка.
- Переводы сообщений агентов не считаются во «входящих» статистики и не влияют на язык собеседника.
- Диагностика: `messageBreakdown` (всего / пользователь / агент), `agentButtons`.

### Пикер «Пользователь vs оператор» понимает «сторону» сообщения
- Если части переписки одинаковые, а сообщения агента отличаются классом выравнивания (`justify-end`, `self-end`, `ml-auto`, `out`…), пикер строит селектор вида **`[общий признак]:not(.класс-стороны)`** — он охватывает и письма, и чат-сообщения пользователя. Проверено на разметке, повторяющей реальный хелпдеск: получен `[data-testid^="conversation-part-id-"]:not(.justify-end)`.
- Атрибуты с номером в конце (`conversation-part-id-464826615`) превращаются в «начинается с» (`[data-testid^="conversation-part-id-"]`) — во всех пикерах.

### «Окно чата» слишком общее
- Причина: пикер строил путь из безликих `div > div > …` (783 совпадения) — тяжёлый обход и дубли сообщений (36 вместо 2).
- Пикер «1. Окно чата» теперь сначала ищет смыслового предка (id, класс, `data-testid`, `role`, `aria-label`), совпадающего не более чем с 3 элементами.
- Если окно всё же совпало больше чем с 30 элементами — сообщения ищутся одним проходом по странице, а самопроверка показывает предупреждение «Окно чата выбрано слишком общо».
- Найденные сообщения без дублей; при вложенных совпадениях берётся самый внутренний элемент.

### Режим заметки — без ложных срабатываний
- В отчёте был `noteModeNow: true` при режиме Email — защита отправки фактически не работала.
- Подпись режима считается активной, только если: выбранная вкладка/переключатель (`aria-selected/pressed/checked=true`, `data-state=active`, класс `active/selected` — у самого элемента или прямого родителя), **или** это кнопка-выпадашка (`aria-haspopup`), на которой написан режим. Пункты меню (`role=menu/menuitem/option`) и обычные кнопки «Note» больше не считаются.
- Диагностика: `noteModeReason` — какой элемент и почему решил, что это заметка.

### Ошибка в «Расширения → Ошибки» (CORS, google.com/sorry)
- Когда Google ограничивает IP, он перенаправляет запрос на страницу проверки `google.com/sorry`; fetch шёл по редиректу и Chrome записывал CORS-ошибку в ошибки расширения, а запрос повторялся 3 раза.
- Теперь `redirect: 'manual'`: перенаправление распознаётся сразу как ограничение (429) → пауза предохранителя, без повторов и без записи CORS-ошибки.
- Проверка орфографии (`dt=qca`) запрашивается **только для текста оператора** в панели ответа (входящие — только перевод): меньше «тяжёлых» запросов; ключ кэша учитывает этот флаг.

### Прочее
- Текст сообщения больше не включает служебные элементы: кнопки (`Reply to this message`), `role=button`, `aria-hidden`, SVG.
- Крошечные служебные фреймы (виджет мессенджера 1×1, кнопка 48×48) не обрабатываются и не участвуют в самопроверке.
- Смена «Сообщение пользователя» или «Сообщения агентов» в настройках сразу перестраивает переводы.

Если оригинал на русском и содержит «вы/ваш» со строчной — кнопка **«Перевести вежливо («Вы»)»**: делает «Вы/Вас/Ваш…» заглавными (подсказка переводчику на вежливую форму) и переводит заново. Если не помогло — совет поправить вручную или через глоссарий.
- Настройка **«Вежливость обращения»** (`formality`): предупреждать / не проверять.
- ⚠️ Насколько заглавное «Вы» меняет выбор Google, проверить на живом API не удалось (Google ограничил запросы с тестового IP) — сама проверка работает независимо от этого.

### 12. Подсказка опечаток
- Бесплатный провайдер запрашивает у Google проверку орфографии исходного текста (`dt=qca`); исправленный вариант возвращается в результате перевода (`spell`), учитывая метки глоссария.
- В панели: плашка **«✏️ Возможно, опечатка. Вариант: «…»»** с кнопкой **«Исправить и перевести»**.
- Настройка **«Подсказывать исправление опечаток»** (`spellCheck`). У официального Cloud API подсказок нет — плашка просто не появляется.
- ⚠️ Формат ответа Google с `dt=qca` на живом API не перепроверен по той же причине; если поле не придёт — функция молча не показывается.

### Прочее
- **Тестовый провайдер «Тестовый — без сети»** (`dev-mock`): переводит как `[es] текст`, определяет язык по ключевым словам, знает несколько опечаток — для проверки интерфейса без расхода лимитов Google. В dev-стенде: `?mock=1`.
- **Ключ кэша переводов включает провайдера** — тестовые переводы не попадают в кэш настоящего.
- **Страница «Sorry… / captcha» от Google** распознаётся как ограничение (429) — срабатывает предохранитель, а не «непонятная ошибка».
- Диагностика: темы, превью, текущий режим заметки, тёмная тема, самопроверка.
- Тестовый чат: тема письма (`#chatSubject`), переключатель **Reply / Note** (`#mode`), тёмная тема `?dark=1`; в dev-стенде `stHarness.message(...)` для эмуляции сообщений фоновой части.

## 0.2.2 — 2026-09-17 — поддержка Shadow DOM

Причина (по отчёту диагностики с реального сайта): интерфейс хелпдеска целиком рисуется внутри открытых Shadow DOM — обычный поиск элементов, наблюдение за изменениями, пикеры и стили туда не проникали; при пустых селекторах переводились служебные надписи всей страницы.

Исправлено / добавлено:
- **Shadow DOM везде**: поиск окон и сообщений, наблюдение за новыми сообщениями, поле ввода и кнопка отправки (защита), ID тикета, язык собеседника, пикеры (выбор элемента под курсором внутри shadow root), диагностика (путь с границей `>>`).
- **Стили подписей подключаются внутрь shadow root** (`content/styles.js`, constructable stylesheets); `content.css` удалён.
- **Без выбранного «Окна чата» перевод не запускается** — больше не переводится весь интерфейс сайта.
- **Пикер «6. Сообщение пользователя vs оператора»**: клик по сообщению пользователя, затем по сообщению оператора — расширение само находит отличающий класс/атрибут.
- Пикер сообщения поднимается от `<p>/<span>` к ближайшему элементу со смысловым классом; утилитарные классы (Tailwind: `flex`, `h-full`, `p-4`…) не попадают в селекторы.
- **Предохранитель лимитов Google**: при 429 или 3 неудачах подряд — пауза 60 с без запросов (или сразу резервный Cloud API, если задан ключ); плашки ошибок сами повторяют перевод после паузы.
- Наблюдение за DOM — троттлинг вместо debounce (на «живых» страницах debounce мог не срабатывать).
- Диагностика: кандидаты в поле ввода и кнопку отправки, число shadow root.
- Тестовый чат: режим `?shadow=1` (весь интерфейс в Shadow DOM).

## 0.2.1 — 2026-09-17 — первые правки после теста на реальном сайте
